# 隧道多視角照片檢視平台 — MVP 規格書

> 狀態：`ready-for-agent` ｜ 來源：需求拷問會議（grilling session）共識
> 範圍：對齊、定位、流暢檢視。標註／報告／OCR 一律不在本期。

---

## Problem Statement

檢測人員以車載 1–8 台相機同步拍攝隧道內壁，每按一次快門產生一組多角度 JPEG。現有痛點：

1. **失焦缺照**：部分相機快門觸發失敗，該時間點完全沒有檔案，各相機資料夾的張數無法對齊。
2. **時間偏移**：相機間**從未對時**，內建時鐘互差可達分鐘級；且拍攝節奏不固定（約每 3–5 秒一按），無法用檔名流水號或修改時間排序。
3. **定位困難**：照片與實體里程（如 `K23+150`）沒有對應關係，找特定瑕疵點極耗時。

## Solution

一個網頁化檢視平台：後端（FastAPI + SQLite）掌管資料與照片串流，前端（React）提供多視角網格檢視。核心能力：

- **時間軸對齊**：以 EXIF 拍攝時間做單調一對一序列對齊，將各相機照片打包成「照片群組」，缺照補 `NULL`。
- **即時里程內插**：人工對著照片輸入實體里程牌數值作為錨點，全線推算里程毫秒級重算、廣播更新。
- **導航**：里程關鍵字跳轉、可縮放的底部導航軌（Scrubber Rail）、鍵盤全程操作。
- **部署形態**：單機 localhost 為主，保留區網多台電腦同時開啟同一隧道的能力（WebSocket 即時同步）。未來目標平台為 Windows。

## User Stories

### 建立與匯入

1. As 檢測人員, I want 以名稱、起迄里程、行進方向建立新隧道專案, so that 後續所有照片與錨點都歸屬到明確的空間座標系。
2. As 檢測人員, I want 一次匯入 1–8 個相機資料夾並為每個視角命名（如 Cam1_拱頂）, so that 系統知道每個資料夾代表畫面上的哪一格。
3. As 檢測人員, I want 系統自動選出序列最完整的相機當基準、算出各機時間偏移 Δt 並允許我手動微調, so that 未對時的相機也能正確對齊。
4. As 檢測人員, I want 匯入前看到對齊預覽（群組總數、各機偏移表、缺照統計、待檢查清單）, so that 我能在寫入資料庫前確認品質。
5. As 檢測人員, I want 照片以 EXIF 拍攝時間排序聚類而非檔名流水號, so that 檔名斷號或亂序不影響正確性。
6. As 檢測人員, I want 缺照的相機時槽自動填入 NULL 並維持固定欄位結構, so that 多視角矩陣永遠對齊同一快門事件。
7. As 檢測人員, I want 對齊殘差异常的照片被標記為「待檢查」而非靜默配對, so that 我能人工複核可疑歸屬。
8. As 檢測人員, I want 取消匯入不留任何副作用, so that 我可以放心重來。
9. As 檢測人員, I want EXIF 缺漏的照片退回檔案修改時間並顯示警告標記, so that 沒有任何一張照片被丟棄。

### 檢視

10. As 檢測人員, I want 鍵盤方向鍵逐群組瀏覽且切換小於 100ms, so that 長距離連續檢視不吃等待。
11. As 檢測人員, I want 中央網格同時呈現該群組所有相機視角且照片版面越大越好、自適應排列, so that 我能一眼比對全部表面。

## Implementation Decisions

### 架構

- **後端**：Python + FastAPI + Uvicorn，SQLite 透過後端 API 存取（瀏覽器不直接碰 DB）。`.venv` 虛擬環境；依賴限純 pip 可安裝者（Windows 友善）。
- **前端**：React + Vite SPA，build 為靜態檔由 FastAPI 一併服務。UI 語言繁體中文。
- **部署形態**：主要情境為單機 localhost；架構天然支援區網——所有 `.db` 與照片必須放在執行伺服器的**本機磁碟**（SQLite 絕不可放網路共用資料夾，有損毀風險），其他電腦以瀏覽器連 HTTP。
- **併發策略**：WAL 模式；所有寫入走單一 API 管道；讀取永不阻塞寫入。每條隧道一個 WebSocket 房間，錨點變更廣播給所有開啟中的檢視端。同一群組錨點同時被兩人修改採**後寫勝**（last-write-wins）；不同群組各自獨立列、無衝突可能。無帳號登入（區网信任環境）。
- **儲存布局**：一個工作目錄 = 一個 `index.db` + N 個隧道 `.db`。

### 資料模型（Schema）

`index.db`

| 資料表 | 欄位要點 |
|---|---|
| `tunnels` | id、name、db_filename、start_mileage_m、end_mileage_m、direction(+1/−1)、camera_count、created_at |

各隧道 `.db`

| 資料表 | 欄位要點 |
|---|---|
| `meta` | key/value：容差、基準相機 id、版本等設定 |
| `cameras` | id、seq、name（視角名）、root_path（相機資料夾根路徑）、dt_offset_sec、photo_count |
| `photos` | id、camera_id、group_id、rel_path（相對於 root_path）、exif_time、corrected_time、time_source(exif/mtime)、flagged(待檢查) |
| `photo_groups` | id、seq、corrected_time、**est_mileage_m（具體化儲存）**、missing_count |
| `anchors` | group_id（UNIQUE FK）、mileage_m、created_at、updated_at |

- 照片檔案**留在原地**（引用路徑，不複製）；每台相機存一個根路徑＋照片相對路徑，換盤符只改根路徑一個欄位。
- 推算里程具體化存進 `photo_groups.est_mileage_m`：錨點變更時以批次 SQL 重算（毫秒級），導航軌渲染與里程搜尋皆可直接範圍查詢。

### 匯入與對齊演算法（正確性核心）

1. 讀取 EXIF `DateTimeOriginal`；缺漏者退回檔案 mtime 並標記警告。
2. 各相機**各自按時間排序**（絕不按檔名）。
3. 基準相機＝照片數最多、序列最完整者。初始偏移 $\Delta t_i = T_{i,\text{first}} - T_{\text{ref},\text{first}}$（各機未對時，偏移可達分鐘級，此法可吸收）。
4. **單調一對一序列對齊**：各相機維護一個只前進的指標，在容差內依序配對；每台相機在每個群組最多貢獻一張（同機雙拍自動另開新群組）；任一相機配不上則該時槽記 `NULL`。此設計保證快門間隔短於容差時也不會混群，且**不產生孤兒照片**（每一張都歸入某群組，僅殘差异常者加旗標）。
5. **偏移修正兩階段**：
   - *完整度搜尋*：各非基準相機候選偏移包含「首張對齊基準前 K 個事件」與「初始 ± j × 中位間隔」，以多相機群組數最大化評分——救回**首張漏拍**造成的整體位移。
   - *中位數迭代精煉*：以各機與基準相機配對差的中位數反覆修正（至收斂），吸收 **EXIF 秒級量化**造成的亞秒系統偏移。
6. 配對殘差 > 容差的 60% → 該照片標記 `flagged`，於匯入預覽的待檢查清單呈現。
7. 群組有效性門檻＝至少 1 張照片；≥1 台缺照即計入 `missing_count`。
8. 容差為匯入參數，預設 **2.0 秒**。⚠️ 實作期修訂：原規劃 0.5 秒，但以 Sony A7RIV 實測（EXIF 秒級解析度＋相機時鐘互差 ±1–2 秒），0.5 秒會將同事件撕裂（297 群僅 4 群完整）；2.0 秒下 73 群四機全滿、僅個位數待檢查。
9. 匯入為**一次性**；事後增補相機＝開新專案重做（不做增量匯入與 ID 重映射）。

### 里程語意

- 格式解析：`K23+150`｜`23K+150`｜`23+150`｜`23150` → 整數公尺（23150）。**不支援小數**。
- 行進方向於建立隧道時指定（遞增或遞減樁號），第 1 群組對應起點里程。
- 內插規則：
  - 無任何錨點 → 依起迄里程對群組序列**等分**初始化。
  - 相鄰錨點之間 → 線性內插。
  - 首末錨點之外 → 以最近錨點段的每群組公尺數**線性外插**。
- 單調防呆：新錨點值必須嚴格落在前一與次一錨點（依群組順序）之間；違反即紅框擋下、不寫入。

### 照片串流與縮圖策略

- 不複製原檔、不做永久縮圖倉庫。
- API 支援寬度參數的動態縮圖端點：後端以 Pillow 即時縮圖回傳，結果寫入**可拋棄的磁碟快取**（keyed by photo id + width，非資料庫、非永久副本，整包刪除無損資料）。
- 網格檢視用縮圖（~1200px 級）；放大超越縮圖解析度時載入原圖串流。

### UI 結構

```
┌──────────────────────────────────────────────────┐
│ 頂欄：隧道名 │ 里程搜尋(Ctrl+G) │ 群組#/推算里程 │ 分頁列 │
├──────────────────────────────────────────────────┤
│                                                  │
│        相機網格（1–8 格自適應、最大化照片面積）        │
│                                                  │
├──────────────────────────────────────────────────┤
│ Scrubber 導航軌（canvas 渲染、可縮放平移）              │
└──────────────────────────────────────────────────┘
      右側抽屜：錨點管理（可收合）
```

- 同步 Pan/Zoom 語意：共用 {倍率, 正規化中心(x%, y%)}——各視角同倍率、同比例位置。**不含**跨表面幾何對位（物理上不存在）。滾輪＝縮放、拖曳＝平移、雙擊＝復原。
- 導航軌：canvas 繪製；藍🔒＝錨點、紅⚠️＝缺照群組、白遊標＝當前位置；單擊跳轉、滾輪縮放軸range、拖曳平移。
- 快捷鍵：`←`/`→` 前後群組｜`Enter` 錨點對話框（預填推算值）｜`Del` 刪當前錨點｜`Home`/`End` 首/末｜滾輪同步縮放｜拖曳同步平移｜`Ctrl+G` 里程跳轉｜`Esc` 關閉彈窗。
- 建立精靈流程：名稱 → 起迄里程＋方向 → 匯入 n 資料夾＋視角命名 → 對齊預覽（Δt 表、群組統計、缺照統計、待檢查清單，可微調偏移）→ 確定寫入。

## Testing Decisions

良好測試只驗外部行為、不綁實作細節。本期三個測試縫（seam），由純到外：

1. **對齊引擎（純函式核心）— 最重要縫**：輸入合成時間序列 fixture（含：首張漏拍、時鐘漂移、同機雙拍、3–5 秒間隔 vs 0.5 秒容差、大量缺照），斷言：群組劃分、Δt 回復精度（中位數精煉後收斂）、flagged 名單、NULL 分佈。此模組的正確性等於整個產品的正確性，測試密度最高。
2. **內插與防呆（純函式）**：零錨點等分、單錨點、多錨點分段、首末外插、單調違規拒絕、里程格式解析四種寫法與非法輸入。
3. **API 整合層（FastAPI TestClient + 暫存目錄）**：匯入→視窗查詢→錨點 CRUD→est_mileage 重算值的端到端斷言；寫入進行中之平行讀取煙霧測試（驗證 WAL 不阻塞承諾）。

前端以手動驗收為主（效能指標即驗收項）；里程解析工具函式可用前端單元測試覆蓋。無既有 prior art（綠地專案）。

## Further Notes

- **漂移風險已評估**：0.5 秒容差下，石英時鐘漂移（約 0.1 秒/小時）在一場拍攝內可忽略；若未來實測尾段配對劣化，容差為匯入參數可直接放寬，演算法不變。
- **交付語意**：`.db` 引用外部照片路徑，備份交付時照片資料夾結構不可變動；僅根路徑前綴可透過設定重映射。
- **術語表**：Photo Group（同一快門事件的多角度照片集合）、Anchor（人工鎖定的實體里程錨點）、Scrubber Rail（底部導航軌）、Δt（相機時鐘偏移）、flagged（對齊殘差异常、待人工複核）。
